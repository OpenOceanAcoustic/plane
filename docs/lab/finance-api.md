# Finance API contract

Base `/api/workspaces/{slug}/lab/`. All money, VC, shares and formula inputs/outputs are decimal strings. No contract/funding-total field exists.

- `GET finance/overview/?project_id=UUID` returns `{manager_id,is_manager,projects:[{id,name,is_lead}],members:[{id,name}],accounts,stages,formulas,forecasts,batches,settlements,commitments,payments,operations,entries,future_plan_limits?}`. Project leads see project funds; members see own forecasts/settlements/commitments/payments, but not project accounts/entries or other members. Public pool manager sees public accounts/entries and project account aggregate only when lead. Optional `future_plan_limits:{[year]:decimal}` provides authoritative workspace-wide annual future-pool compilation limits for the designated workspace finance manager, including when a project filter is selected; other users receive an empty map. Years use the workspace timezone and fact dates. Each limit counts unreversed receipt/opening credits and subtracts unreversed compilation debits for that year. The aggregate includes funding from projects the manager cannot otherwise inspect, without disclosing those projects' source operations or entries.
- `GET finance/entries/?project_id=UUID&format=csv` exports visible append-only entries (JSON by default).
- `GET/POST finance/formulas/<uuid:project_id>/`: GET `{templates:[{name,task_expression,member_expression}],versions:[{id,project_id,version,task_expression,member_expression,parameters,reason,actor,created_at}]}`; POST `{task_expression,member_expression,parameters:[{name,scope:'task'|'member'|'stage',unit,source,default?:decimal}],reason}` returns formula row. Defaults: task `E * 0.2 * VC / B`; member `E * (0.5 * b + 0.3 * r + 0.2 * VC / B)`.
- `POST finance/preview/<uuid:project_id>/`: `{task_expression,member_expression,parameters:[...],inputs:{E,B,VC,b,r,...},kind:'task'|'member'}` -> `{result,inputs}`; does not save or authorize payment.
- `POST finance/forecast/`: `{stage_id,kind:'task'|'member',basis:'budget'|'received',bounty_id? (task required),user_id? (member required),parameters:{customName:decimal}}` -> forecast row `{id,stage_id,kind,basis,bounty_id,user_id,formula_id,formula_version,expression,inputs,result,created_at}`. E/B/VC/b/r come from authoritative records. Only project leads save task forecasts; these are the published card references. Members can save their own member forecasts. Task uses planned budget VC for budget basis and awarded VC for received basis. Member uses frozen planned_vc for budget and own awarded VC for received.
- `POST finance/<action>/`: every action includes UUID `request_key` (idempotent), `reason` (nonblank), optional `evidence` string (receipt/payment should include proof reference), optional ISO `occurred_at` (fact date, never replaces recorded created_at). Response `{ok:true,id,operation_id}`. Validation errors return HTTP 400 with a DRF message array (or a field `error` for malformed model IDs); permission errors return HTTP 403 with `detail`.

Actions/payloads:

- `manager`: `{user_id}`; only current designated manager, or earliest active workspace administrator for initial designation. Before the first finance mutation, overview reports that candidate without creating policy records; the first authorized mutation persists the designation. Manager must be active administrator.
- `stage`: `{stage_id,E,purposes:[{name,amount}],members:[{user_id,b,r,planned_vc}],upgraded:boolean,history:[{user_id,vc,funding_source,qualified_at:'YYYY-MM-DD',basis,share?}]}`. One frozen plan per existing stage B; purposes sum E, b/r sum <=1, historical shares are frozen by source VC ratio. Historical qualification requires evidence; each funded amount is eligible only from qualified_at through 36 calendar months later, and only within its original or explicitly inherited funding source. Creates project/stage accounts. No default evenly distributed shares.
- `receipt`: `{stage_id,gross,costs,D,source,evidence}`. Actual receipt gross, cost deduction paid once, D <= gross-costs. D partitions future15%,public10%,risk5%,member70%; upgraded member splits history10%/execution90%. Remaining cash stays project. Each receipt batch freezes original historical eligibility.
- `opening`: `{project_id? (omit for public),stage_id?,kind,amount,source,evidence}` imports evidenced opening balance; risk/history imports create an original opening batch (D=0, no repeated split) so subsequent batch risk-use/release and frozen historical qualification remain traceable; execution/history require stage, historical requires upgraded qualification. Public accounts only designated manager; project accounts only project lead.
- `transfer`: `{from_account_id,to_account_id,amount}`; source and destination must both be manageable by actor; prevents unfunded stage allocation. Stage reward accounts cannot be arbitrary transfer source/destination; use receipt, risk-release, carryover/dispute actions.
- `expense`: `{account_id,amount,purpose,user_id?,evidence}`; eligible project/retained/public/research/exploration funds only, rewards use settlements/payments.
- `settlement`: `{stage_id,user_id,amount,performance_basis,forecast_id?}` records member cumulative execution final amount (new immutable revision), total final <= funded stage execution allowance; cannot reduce below paid plus remaining commitments.
- `history-settlement`: `{stage_id}` freezes accrued historical amount by original qualification snapshots, subtracting existing cumulative awards; no generic execution formula.
- `commit`: `{settlement_id,amount}` reserves payment portion against funded available cash and settlement unpaid/uncommitted balance; cannot reserve twice.
- `cancel-commit`: `{commitment_id}` releases unpaid remaining reservation.
- `payment`: `{commitment_id,gross,withheld,evidence,reference}` net=gross-withheld; records offline net outflow and withholding payable separately, consumes gross reservation. Withheld tax stays in withholding account until tax-remit.
- `tax-remit`: `{account_id,amount,evidence}` records offline tax outflow.
- `risk-release`: `{batch_id,amount,evidence}` original risk account -> original stage execution/history in original 90/10 split; no repeated 15/10/5 extraction (future/public/risk). Cannot exceed batch unreleased risk. Must confirm additional execution award separately.
- `future-plan`: `{year,amount}` designated manager moves uncommitted future_pool balance 70% research /30% exploration (annual amount must equal that year's new receipts not previously compiled).
- `dispute`: `{from_account_id,amount}` project lead reserves unsettled stage execution funds into stage dispute account; settlement budget reduced accordingly. `resolve-dispute`: `{from_account_id,to_account_id,amount}` sends dispute to original execution account only.
- `carryover`: `{from_account_id,amount}` unused execution -> retained account, without moving settlement/commitment obligations.
- `stage-allocation`: `{from_account_id,stage_id,amount}` project lead explicitly moves available retained balance to a different frozen stage execution account in the same project. Source must be retained, target must be another frozen stage; cross-project/account spoofing is rejected. No repeated D extraction; new stage final awards require separate confirmation.
- `reverse`: `{operation_id,evidence}` adds compensating entries. Rejects consumed funds, consequential settlement/commitments, and already reversed original records; does not edit historical ledger.
- `receipt-delete`: `{batch_id,evidence?}` deletes an erroneous receipt through an immutable operation linked to the original operation and compensating entries. Requires project-lead authorization, a UUID request key and a nonblank deletion reason; supplemental evidence is optional. Original batch and evidence remain readable. Rejects consequential batch-risk processing and insufficient balances, approved awards or cash commitments. Does not alter another installment or create an automatic payable.
- `stage-delete` / `stage-restore`: `{stage_id}` deactivates/restores a stage budget using immutable operation markers. Deletion requires no remaining cash obligations, balances or unfinished bounties. Frozen plans, formula snapshots, earned VC and ledger rows remain unchanged. A deleted stage rejects new business until explicitly restored; restore also requires its financial project to be active.
- `project-delete` / `project-restore`: `{project_id}` deactivates/restores this project's financial configuration. Uses the current project lead and workspace finance lock, checks all affected stages/accounts and unfinished bounties, and never deletes the native project or work items. Historical queries and exports remain permission restricted and available.

Deletion metadata supplements overview rows: projects include `deleted`/`finance_deleted`, `can_delete`, `delete_reason`; stages include `deleted`, `can_delete`, `delete_reason`, `can_restore`; batches include `operation_id`, `kind:'receipt'|'opening'`, `occurred_at`, `reversed`, `can_delete`, `delete_reason`. Normal UI hides deleted records; the history toggle exposes them. Receipt totals exclude reversed batches and opening balances, and use decimal arithmetic. Deletion requests and their replays share the existing workspace lock and request-key boundary. A reversal checks every original entry's financial project and stage, including a different source stage, before writing compensating entries.

Overview row fields:

- account `{id,project_id,stage_id,kind,label,balance,committed,available,can_manage}`.
- stage `{id,stage_id,project_id,name,B,E,purposes,members,upgraded,history,execution_funded,history_funded,formula_version,can_manage}`.
- settlement `{id,stage_id,user_id,user_name,kind:'execution'|'history',revision,amount,forecast_id,forecast_amount,difference,performance_basis,paid,withheld,net_paid,outstanding,committed,can_manage}` only latest cumulative revision.
- commitment `{id,settlement_id,account_id,user_id,amount,paid,remaining,cancelled,can_manage}`.
- payment `{id,commitment_id,settlement_id,user_id,gross,withheld,net,evidence,reference,created_at,occurred_at,reversed}`.
- batch `{id,stage_id,project_id,gross,costs,D,source,risk,execution,history,risk_released,risk_remaining,history_snapshot,created_at,can_manage}`.
- entry `{id,operation_id,account_id,project_id,stage_id,kind,delta,reason,evidence,actor,created_at,occurred_at,reverses_id}`.
- operation `{id,kind,actor,reason,evidence,payload,created_at,occurred_at,reverses_id,reversed,can_manage}`.

`GET finance/workflow/?project_id=UUID` (alias `finance/flow/`) and `GET projects/<uuid:project_id>/workflow/` use the shared contract `{scope,project_id,title,active_node_ids,nodes,edges,history,actions}`. Nodes are `{id,label,x,y,state:'completed'|'current'|'upcoming'}`, edges `{id,source,target}`, history `{id,label,node_id,actor,created_at,reason,source:{path,label}|null,occurred_at?,evidence?,snapshot?}`, and actions `{id,action,label,node_id,body,enabled,reason}`. Stages and receipt batches are parallel branches; project archive and financial settlement are independent statuses. All projection GETs are read-only. Source history preserves formula/parameter snapshots and fact dates. Enabled actions invoke the same permission-checked services as normal finance forms.

Money/VC calculations always use Decimal through card projections and serialize decimal strings. Percent splits round down separately to cents; remainder stays in its source account (project, risk or future pool). No tail is silently assigned to a member. Future fiscal years and historical qualification dates use the workspace timezone (Asia/Shanghai by default). Formula AST arithmetic supports bounded four operations, parentheses and min/max only; no code evaluation.

Finance and bounty forms compare entered decimal values with the selected source's available allowance while typing. An amount above that allowance immediately shows a field error and disables save/publication; correcting the amount or selecting another source recalculates the limit. Lower bounds, withholding versus gross and cumulative awards versus prior payments/contributions are also checked where applicable. Server-side permission, Decimal validation, locking and idempotency remain authoritative when balances change concurrently; rejected bounty publication/claims refresh the current allowance while retaining entered task/delivery materials for a corrected retry.

Additional public/risk actions and fields:

- `risk-use`: `{batch_id,amount,category:'refund'|'rework',purpose,evidence}` records approved offline responsibility expense against that original batch's actual risk reserve, with provenance. Batch adds `risk_used`; `risk_released` excludes used reserves.
- `exploration-allocation`: `{stage_id,amount}` designated manager moves future_exploration to a frozen stage execution allowance, without redistributing D. Overview `funding_targets:[{stage_id,project_id,project,name,E}]` supplies manager-approved stage references.
- `public-duty`: `{user_id,period:'YYYY-MM',duty,amount,award_id?}` designated manager approves a fixed monthly duty amount. Optional latest award_id appends cumulative revision for that same member/month. Revision may reduce to zero only when paid and outstanding commitments are zero; the original award remains unchanged. No VC formula/ranking applies. Cannot reduce below paid + existing commitments or exceed available public pool funding.
- `public-commit`: `{award_id,amount}` reserves monthly public-duty award payment. `public-cancel-commit`: `{commitment_id}` releases unpaid reservation. `public-payment`: `{commitment_id,gross,withheld,evidence,reference}` records offline partial payment (same gross/net/withholding accounting as project rewards).
- `tax-remit` also accepts the stage-less public withholding account.
- Overview adds `public_awards:[{id,group_key,revision,user_id,user_name,period,duty,amount,paid,outstanding,committed,withheld,net_paid,can_manage}]`, `public_commitments:[{id,award_id,user_id,user_name,account_id,amount,paid,remaining,cancelled,can_manage}]`, `public_payments:[{id,commitment_id,award_id,user_id,gross,withheld,net,evidence,reference,created_at,occurred_at,reversed}]`. Nonmanager users receive only their own rows.
- `members` adds `is_admin`; only those members are eligible for manager designation.
- Stage `history` entries require `{user_id,vc,funding_source,qualified_at:'YYYY-MM-DD',basis,share?}`. share is calculated from frozen valid VC / source total VC; supplied share must agree. `qualified_at` starts the 36-calendar-month eligibility window. Each receipt qualification is checked against its own occurred_at within that window; expired portions stay unallocated, never renormalized among others. Same source retains initial snapshot denominator. Distinct later source has no automatic historical right: matching explicit history must supply `inherited_from` (initial source) and `source_basis` as evidence of authorized inheritance.
- Bounty card projection uses `{stage_budget:B,reward_estimate:{amount,formula_version,error?},received_estimate:{amount,formula_version,error?}|null}`. Public summary gets numeric budget reward/version only; received projection is restricted to leads and confirmed participants. Formula inputs, full E and cash ledgers are not included in the public bounty projection.

Bounty deletion and work-item overview:

- `DELETE bounties/<uuid:id>/detail/` with `{reason}` returns 204. Requires the current project lead with active member permissions. Repeated/concurrent deletion records one audit, changes status to `deleted`, releases only unawarded VC, revokes task grants/material shares and removes the card from hall/inbox/native badge metadata. Source work item, planning, blocks, colors and earned VC/cash history remain unchanged. `issue_id_snapshot` preserves the source after unlinking the native issue so it can be published again.
- Bounty detail adds `can_delete`; deleted detail/history remain read-only for authorized original-project users. Mutating task operations and sharing reject deleted records.
- `GET ledger/` rows add authoritative `can_reverse` for an unreversed positive VC entry when the actor is the current eligible project lead. It remains available after bounty deletion and is independent of hall visibility.
- Planner items and visible calendar events add `can_open_issue`, based on native issue read access rather than edit access. Task-only participation never sets this flag. Hidden calendar events retain only neutral busy information.

Project VC budget and simplified bounty publication:

- `POST stages/` accepts `{project_id,name,budget,append?:boolean,reason?,request_key?}` for an active project administrator (role 20), even with no `project_lead`. The web VC form sends `append:true`: the first installment initializes Stage, and later installments join that current Stage instead of replacing the source. Omitting `append` retains the legacy creation of an independent frozen stage for existing financial phase workflows. A `VCBudgetEntry` preserves each initial amount; effective VC is the sum of its current entry amounts. UUID request keys replay the same actor/payload without adding funds twice. Existing independent historical stages and frozen cash denominators are preserved.
- `GET bounties/budgets/` returns `[{project_id,project,stage_id,stage_name,budget,reserved,available,configured,wallet,can_allocate,publication_source,entries,...}]` for active project members. `publication_source` is `project` for current administrators and `personal` for other members. `entries:[{id,name,initial_amount,amount,minimum,revision,created_at}]` lists current installments. `minimum=max(0,reserved-(budget-entry.amount))`; `reserved` includes net member grants, historical direct reservations, and new direct-project funding commitments. Personal-funded bounties do not reserve project principal again. Unconfigured projects have null numeric/source IDs and an empty entry list.
- `GET tasks/?project_id=UUID&publishable=1&q=...` returns available top-level, unstarted backlog/todo work items in that project, excluding drafts, archived/deleted items and existing active bounty associations. Query text is optional; normal task search retains its existing behavior and access checks.
- `POST bounties/` accepts `{project_id,issue_id,budget,project_vc?,earned_vc?,request_key?,public_summary,deliverable,criteria,reviewer_id,...}`. Current project administrators publish from unallocated project VC directly, without a self grant or personal payment fields; personal balances stay unchanged. Other members combine assigned and earned same-project VC, defaulting to quota first. Funding records retain `source:project|personal` permanently, so later role changes do not switch a bounty's source. All new publications retain publisher management and idempotent request keys. The legacy `stage_id` route resolves the current project source using these same permissions and limits.
- Publisher, acceptance reviewer and major-task publication/acceptance reviewer may be the same eligible project member. The selected reviewers must remain active workspace/project members with the required project role. Major publication still enters `publication_review`; acceptance still enters `acceptance_review` and creates no earned VC until that separate review action succeeds. Each action retains its designated-role authorization and audit record. Reviewers cannot claim a team allocation or accept a task in which they have an approved allocation, including participation added through another channel.
- Bounty hall/detail projections add `claim_available:decimal = max(0,budget-sum(all approved allocation.planned))`. Pending applications do not reserve a portion, and already awarded VC is not subtracted a second time. Public summaries return this aggregate while retaining the existing filter that hides other participants' details. `can_claim` is false when no allowance remains. `POST bounties/<uuid:id>/claim/` checks the submitted planned VC against this current balance under the existing bounty/stage locks; approval separately rechecks the same team budget. Claim and cumulative acceptance inputs show immediate allowance errors rather than waiting for submission.
- Hall publication writes material once and submits the same deliverable/criteria as public and execution fields. Publication freezes VC only; acceptance records earned VC, and cash confirmation/payment remain independent. New publications are managed by their original publisher while that user remains an eligible project member; historical `member_funded:false` bounties retain current project-lead management. Self-claim is forbidden for member-funded bounties. Completion/rejection/cancellation/deletion returns only unawarded funds to the original publisher's same-project wallet (project quota is consumed first). Bounty projections add `member_funded,publisher_id` and manager-only `funding:{project_vc,earned_vc}`. Contribution reversals remain append-only; spent earnings become `earned_debt` and offset future earnings rather than manufacturing available VC. Reopening a corrected member-funded bounty must reserve the released funding again.

### Member VC quota administration

- `GET bounties/quotas/<project_id>/` requires an active project administrator (project role 20 and valid workspace membership), independently of finance delegation or the `project_lead` field. Returns `{members:[{id,name,wallet,reclaimable}],history:[{id,user_id,name,delta,reason,created_at}]}`. Ordinary members use their own wallet in `bounties/budgets/` and cannot read these member balances or grant records.
- `POST bounties/quotas/<project_id>/` accepts `{request_key,user_id,amount,kind:'grant'|'reclaim',reason,stage_id?}`. Requires the same administrator permission. Positive decimal `amount` and a nonblank reason (<=4000 characters) are mandatory. A grant reserves current-stage unallocated principal and credits that member's project quota. A reclaim cannot exceed either that stage's net grant or the member's uncommitted project quota, and never confiscates earned VC. Optional `stage_id` rejects a changed source. Request-key replay returns 200 with the original ID; creation returns 201; changed actor/body is rejected. Grant history is immutable at database level; reclaim appends a negative grant. Grant and publication serialize with acceptance/reversal through the existing transaction lock, preventing concurrent over-allocation or double spending.
- The finance screen shows current project VC budget balances and a separate VC ledger/export tab. Existing stages, forecasts, settlement/cash records and historical qualifications remain unchanged when a new budget is set.
- The bounty workflow canvas defaults to the main flow, with major-review stages included when required and only relevant exception/history branches visible. “全部流转” reveals the original available transitions, “主流程” restores the compact view, and “当前阶段” focuses the current node. Display filtering does not change server workflow nodes, actions, permissions or retained history.

## Project finance delegation

`GET finance/permissions/?project_id=<uuid>` lists active project members and their finance permissions.
`POST finance/permissions/` accepts `{project_id,user_id,permissions}`. Permissions are `view`, `record`, `approve`, and `pay`; any write permission also includes `view`. An empty list revokes the grant. Grants apply only to the selected project and stop working when workspace/project membership is revoked or the member becomes a guest.

Project creators, current project leads, and workspace administrators with active project membership retain all project finance permissions and can grant/revoke other members' access. Their own permissions cannot be removed by a grant. Delegates cannot grant access or delete/restore a finance project or stage. Public-pool management remains available to all active workspace administrators after a designated manager changes.

`record` covers cash budgets, receipts, opening balances, internal transfers and reserves. `approve` covers final reward approval and reward formulas. `pay` covers payment scheduling/cancellation, offline payment, external expenses, risk-reserve expenditure and tax remittance. Reversal requires the permission of the original operation. Overview projects include `permissions`, `can_manage_permissions`, and `allowed_actions`; web and Android use the same server rules.

## Web bounty quotes

All paths below are relative to the workspace lab API. Existing `claim`, `approve` and `confirm` contracts remain available for legacy applications. New quotes are separate records; an `Allocation` is created only on final approval, with `approved` and `confirmed` true. No contribution or cash entry is created.

- `GET bounties/<id>/quotes/` returns `{quotes,can_apply,available,funding_source,project_available,quote_limit,reviewers,file_size_limit}`. Each visible quote includes `id,user_id,name,revision,kind,vc,available_at_submission,deliverable,basis,status,created_at,reviewer_id,allocation_id,attachments,history,can_approve,can_reject,can_review`. Approvers additionally receive `budget_snapshot` and `adjustment:{additional,next_budget,source_available,requires_review,funded}`. Quotes, evidence and history are restricted to the applicant, eligible bounty manager (publisher for member-funded bounties, current project lead for historical ones), and designated eligible quote reviewer. Project administrator status alone does not disclose another publisher's negotiations.
- `POST bounties/<id>/quotes/` accepts `{request_key,kind:'original'|'negotiated',vc,deliverable,basis?,attachment_ids?:[]}`. Positive decimal VC has at most two fractional digits. Original VC must equal the current positive remaining balance; a changed price returns 409. Negotiated quotes require nonblank basis or an owned attachment and may exceed the bounty price. For project-funded bounties, `quote_limit = available + project_available`: unassigned bounty VC plus unallocated VC in its original project budget, counting the existing reservation once. A quote above the current limit returns 409 and the web form refreshes the limit while retaining the draft. Personal-funded bounties return null for these two limit fields to preserve wallet privacy; approval still checks the publisher's same-project funds. Delivery/basis each allow 4000 characters and at most 20 attachments. One pending/pending-review quote per applicant and bounty; rejected applications can be submitted as new immutable revisions. Legacy allocations block new quotes, and pending new quotes block legacy claims.
- `POST bounties/<id>/quotes/<quote_id>/approve/` accepts `{request_key,expected_budget,reviewer_id?,reason?}`; `expected_budget` is the exact snapshot from the quote projection. The eligible publisher approves member-funded bounties; the current eligible lead approves historical project-funded bounties. Final approval tops up `budget` and `reserved` by `max(0,approved_plans+quote.vc-budget)` using unallocated project principal for administrator project-funded publications and historical ones, or the publisher's remaining same-project quota/income (quota first) for personal-funded publications. A 5000 VC bounty with a 6000 VC quote reserves only an additional 1000 VC at final approval. It grants task access and retains existing personal planning references. Funding snapshots record `funding:'project'|'personal'`; only personal funding includes the private wallet balances. Stale source balances or publisher eligibility invalidate approval.
- Additional VC for an already-major bounty, or one whose new total reaches 40 VC or exceeds 20% of the original Stage budget, changes quote status to `pending_review` without reserving funds. A qualified nonparticipant reviewer must be selected (or the existing independent reviewer is reused). `POST .../review/` accepts `{request_key,expected_budget,decision:'approve'|'reject',reason?}`. Approval rechecks the saved budget, allocations, manager identity/eligibility and member-wallet balances where applicable; a stale snapshot returns to `pending`, logs the reason and responds 409. Final review applies the top-up and major-task classification together.
- `POST .../reject/` accepts `{request_key,reason}`. A nonblank reason is also mandatory for a review rejection. Request keys replay the original submission/decision without repeating side effects and reject changed actors or payloads.
- `POST bounties/<id>/quote-attachments/` accepts one multipart `file` and returns `{id,name,size,download_path}`. Uploaded files are scoped to the applicant and bounty, and can be attached once to a submitted quote. `GET bounties/<id>/quote-attachments/<attachment_id>/` rechecks access and streams an attachment with `private, no-store` and `nosniff`; it never returns native asset or storage URLs. The dedicated `lab_quotes` storage overrides public-read ACLs with private object ACLs. Deployments must keep this storage/prefix inaccessible to anonymous bucket reads.

Quote states are `pending`, `pending_review`, `approved`, `rejected`, `closed`. Starting, cancelling or deleting the bounty closes all unprocessed quotes with history. Quotes are accepted only while the bounty is open and its source task and finance configuration remain usable. `can_apply` permits negotiation even at zero remaining VC.

Bounty projections add the caller's `has_quote` flag for “我的参与”. Inbox adds quote approval/review tasks with a web marker. `GET bounties/<id>/workflow/?quotes=1` includes only authorized quote history, adds the price-review node when relevant and omits the confirmation node when there are no legacy allocations. The workflow endpoint without this opt-in retains the legacy graph. Final allocation VC follows existing task visibility.

The test uses Django's live test server and separate real sessions for applicant, lead and reviewer; it never connects to a running production API. Fixtures and session cookies remain private temporary files; tracing, screenshots and videos are disabled.

Migration `0019_member_vc_wallets` adds tables and a default-false bounty field; historical bounties keep their manager and budget behavior. Once any new grant or member-funding row exists, do not roll back to application code that ignores these balances. Preserve the new accounting schema and fix forward, or perform an explicitly planned, quiesced restore with a consistent database/uploads backup. A code-only rollback that forgets grants could allow project principal to be spent twice.

- `PATCH bounties/budgets/<project_id>/entries/<entry_id>/` accepts `{amount,expected_revision,reason,request_key}` for an active project administrator. Amount may be zero. It replaces that entry's current amount under the shared workspace finance/WIP lock, rejecting any project total below net grants plus direct bounty commitments. Concurrent publication, grants, reductions, stale revisions and changed request-key payloads are checked atomically. The audit records before/after amounts and reason; the initial amount and frozen Stage amount remain unchanged. Quote approval snapshots include the effective pool total, so later budget changes require a fresh approval.

Personal workload advice:

- `GET me/workload/` returns only the authenticated member's current-workspace counts: `{active,major,active_limit,major_limit,overloaded,blocking:false,message}`. Counts share native `lab_work()` identities across projects; native assignment plus bounty participation count once. Query parameters never select another member. Default recommendations are 2 active and 1 major; current approved legacy exceptions can raise these recommendations. No task names, IDs or other members' workload are returned.
- `0023_wip_reminders` replaces only `lab_wip_validate(uuid)` workload rejection with a no-op. Existing transaction locks, native workflow guards, budget checks and immutable accounting triggers remain. Counts above recommendations no longer reject native/API mutations, team start or reacceptance. The historical `wip-exceptions/` interface and approval permissions remain compatible and affect advice only.
